# Mobile-first UI and household URLs

## Context and goals

The current dashboard repeats the navigation, the desktop header does not give mobile users a clear set of destinations or indicate the active section, and switching households requires selecting a value and submitting a form. Most household pages use the session-selected household rather than one identified by the URL. On the income and spending forms, the select chevron sits against the field border.

Make the most common flow—opening a household and recording an entry—clear on a phone. Give each household page a canonical, bookmarkable URL, and make the navigation reflect that URL. Keep the existing server-rendered Go templates, Tailwind CSS, and progressive HTMX. This plan builds on the [MVP baseline](./20261108_201136_budget_tracker_mvp_plan.md); it does not change `/api/v1`, the data model, finance rules, or household roles. A new dashboard with summaries is out of scope.

## Confirmed product decisions

- **Entries is home.** Remove the dashboard as a destination, along with its repeated links and permanent readiness banner. Put **Add spending** and **Add income** above the entry list, with a useful empty state. Use compact rows on phones rather than forcing the desktop table into a narrow viewport. Reports remains the place for converted totals and missing-rate warnings.
- **One canonical URL per page.** Use `/app/{householdID}/…`, not `/app/households/{householdID}/…`. `/app` redirects to `/app/{householdID}`, which redirects to `/app/{householdID}/entries`. Neither entry point renders Entries. Navigation and picker links go directly to canonical destinations.
- **The URL determines the household.** Use an existing stable household ID in the path and show the household name in the UI. Never use a session preference or a submitted field to override the household on a scoped request.
- **Navigation stays at the top and follows the route.** Use **Entries**, **Reports**, and **More** in the desktop header and in a collapsible hamburger menu in the mobile header. Do not use a bottom navigation bar. Highlight the section for nested pages as well as its landing page.
- **Keep native form controls.** Give selects an inset chevron and enough trailing padding, without replacing the native picker. Stack Currency and Date on narrow screens; keep editable defaults and optional Description so a new entry normally requires only Amount.

## Routing and household context

| HTML URL | Behavior |
| --- | --- |
| `/app` | Redirect to `/app/{householdID}` for the last-used accessible household; use a deterministic accessible fallback if the preference is absent or stale. If there are no memberships, redirect to onboarding. |
| `/app/{householdID}` | Check membership, then redirect to `/app/{householdID}/entries`. |
| `/app/{householdID}/entries` | Canonical landing page. Keep existing list filters and pagination in the query string. |
| `/app/{householdID}/incomes/…`, `/app/{householdID}/spendings/…` | Canonical create/edit pages and scoped mutation endpoints. |
| `/app/{householdID}/reports`, `/app/{householdID}/exchange-rates` | Canonical report and rate pages; scope nested rate actions as well. |
| `/app/{householdID}/preferences`, `/app/{householdID}/settings` | Household-specific personal preferences and admin settings. Put settings mutations, including invitation management, under the same household prefix. |
| `/app/households/new` | Keep a separate household-creation page outside household context. Public invitation links retain their existing URLs. |

- Resolve and validate the path ID for every scoped request, including fragments and writes. Use the shared services for authorization and persistence; verify that a resource belongs to the URL household before acting on it. Invalid, missing, or inaccessible household IDs return an error rather than loading a different household. Preserve existing CSRF and role checks.
- Keep the session household as a landing preference only. Remember the household on authorized full-page visits; a preference-store failure must not change the household of an otherwise valid request. Forms already open in another tab keep their original scope, even after the preference changes.
- Centralize scoped URL construction for links, form actions, HTMX request URLs, and redirects. Preserve canonical deep links through login and take successful creation and invitation acceptance to the appropriate household. Keep list/report filter state in the URL when applying filters, including with HTMX.
- The app is not deployed, so no legacy URL migration is needed. At cutover, remove the replaced GET and POST routes rather than adding compatibility redirects or forwarding writes. Remove the switch POST once the picker uses links. Keep the `/app` and `/app/{householdID}` redirect entry points, household creation, and public invitation routes as specified above. Test the full `net/http` route table for conflicts before cutover.

## Mobile shell and forms

- Keep a compact header with the current household name visible, including on full-page income and spending forms. Opening the picker shows the current household with a checkmark, other households as direct links, and **Create household**. Use a disclosure that works without JavaScript. With no safe equivalent destination (for example, on an edit form), switch to the target household’s Entries page. For equivalent lists like Reports, keep the section but drop household-specific filters, resource IDs, and drafts.
- Use a compact hamburger disclosure in the mobile header that works without JavaScript. Give it an accessible name, such as **Menu**. **More** exposes Exchange rates, Preferences, admin-only Household settings, and Sign out. Account and household administration should not compete with the recording actions on Entries.
- Derive the active section server-side from the matched route, not a raw URL prefix, query string, or click history. Income and spending forms belong to Entries; rates, preferences, and settings belong to More. Use a visual cue beyond color, visible keyboard focus, and `aria-current="page"` on the exact current destination link, not on a disclosure trigger or parent link for a nested page.
- Aim for touch targets of at least 44 CSS pixels. Keep Save and the final fields reachable when the on-screen keyboard is open. Use a shared select style, reserve space for the chevron with long labels, and check high-contrast and keyboard behavior. Keep attribution and role-specific controls intact.

## Delivery milestones

| Milestone | Deliverable |
| --- | --- |
| 1. Scoped routing | Add the canonical route family, shared request context and URL builders, and redirect entry points. Migrate links, form actions, HTMX responses, auth/onboarding destinations, and route tests in small working slices. Remove the replaced routes after their callers use canonical URLs. |
| 2. Responsive shell | Ship the household picker and URL-driven shared navigation. Move secondary destinations under More and retire the old switch UI and POST together. |
| 3. Entries and forms | Make the canonical Entries page the only landing content, retire the dashboard template, improve list rows and empty states on phones, and share the native select styling across forms. |
| 4. Verification | Run automated checks and the responsive smoke matrix below, and update affected documentation before marking the plan complete. |

Keep each commit buildable and testable; include relevant tests with the behavior they cover. Routing and URL generation must be available before a UI change links to them.

## Acceptance and validation

- Server tests cover both redirect hops, onboarding, a stale landing preference, authentication and canonical deep links, and canonical link/form targets. Verify that removed routes do not redirect to a household or accept writes. A scoped request never serves another household when its ID is invalid or inaccessible.
- PostgreSQL integration tests cover two household tabs in the same session: open an entry form in A, navigate to B, then submit A and verify the record exists only in A. Exercise plain HTML and HTMX, including validation re-renders and success redirects. Verify mismatched resource IDs cannot be edited or deleted and that member/admin role rules remain intact.
- Verify bookmarked and refreshed Entries/Reports URLs restore relevant filters, browser Back/Forward restores the household and active section, and the picker links go directly to the target URL without a submit. Full-page navigation, the mobile menu, forms, and the picker work with JavaScript disabled.
- Smoke-test at 320 px, a typical phone width, and desktop. Test Safari on iOS and Chrome on Android (or representative emulation, with any device gaps recorded). Complete add-spending and add-income flows; check long household and currency names, mobile keyboard and Save visibility, focus and active cues, and no page-level horizontal overflow. Check report missing-rate warnings remain visible.
- Run `mise run check:all` with local PostgreSQL available; use `mise run dev` for browser smoke checks. Record actual results as work lands.
